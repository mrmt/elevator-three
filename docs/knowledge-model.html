ELEVATOR-THREE / MUSIC SYSTEM NOTES

elevator-three の音楽知識モデル

知識・状態・記憶・制約・判断・演奏という観点から、自動演奏システムの内側を読み解く

はじめに ― コードの中にある「音楽知識」を分離して考える

elevator-three は elevator-two から分岐した楽器で、音源と音楽的な規則は elevator-two と同じものを持つ。違いは判断の一部を外部のモデル Jev に相談する点にある。以下では、両者に共通する知識のモデルを整理し、そのどこに Jev が入ったのかを示す。

elevator-three には、多数のアルゴリズム、確率、パラメータ、音源回路が存在する。しかし、それらを実装の集合としてだけ見ると、このシステムがなぜ音楽として成立するのかが見えにくい。

そこで、現在の実装から一段抽象化し、elevator-three が持っているものを音楽知識モデルとして整理する。

ここでいう音楽知識とは、音楽理論だけではない。

  • 何を守るべきか
  • 何なら変えてよいか
  • どの時間スケールで判断するか
  • 現在の状況をどう分類するか
  • 過去の演奏を何をどこまで覚えるか
  • どんな条件なら何を鳴らすか
  • いつ鳴らさないか
  • どの変化なら「同じものの変奏」と聞こえるか

までを含む。

elevator-three は、この知識を使って状態を観察し、判断し、演奏行為へ変換するシステムと考えることができる。

1. 全体モデル

最も単純化すると、elevator-three は次の循環で動く。

            ┌───────────────┐
            │   音楽知識     │
            │ rules / taste │
            └───────┬───────┘
                    │
                    ▼
┌─────────┐   ┌───────────────┐   ┌─────────────┐
│  記憶    │──▶│   現在の状態   │──▶│    判断      │
│ memory  │   │ musical state │   │ decisions   │
└────▲────┘   └───────────────┘   └──────┬──────┘
     │                                    │
     │                                    ▼
     │                              ┌─────────────┐
     └──────────────────────────────│   演奏行為   │
                                    │ performance │
                                    └─────────────┘

重要なのは、乱数はこの図の中心ではないことだ。

乱数は判断の候補から一つを選ぶ道具であり、候補そのもの、選んでよい条件、選んではいけない条件は音楽知識によって決められる。

elevator-three では、この「判断」の箱が三つに分かれる。

判断 decisions
 ├─ 音楽知識   候補を作り、不適切なものを除く        (elevator-two と同じ)
 ├─ Jev        残った候補に、流れを踏まえた確率を付ける (elevator-three で追加)
 └─ 手元の乱数 Jev の確率に従って引く。
               Jev に任せない割合の判断と、答えが間に合わないときは
               elevator-two と同じ固定の確率で引く

Jev に渡るのは「現在の状態」と「記憶」の一部を言葉と記号にしたもので、Jev が返すのは確率だけである。候補の外を選ぶことはできない。

2. 知識は六種類に分けられる

現在のelevator-threeの知識は、概念的には六種類に整理できる。

2.1 不変条件 ― 守らなければ音楽の骨格が壊れるもの

例:

  • 基本の拍子感は4/4に置く
  • キックは4つ打ちを基本とする
  • 小節頭のベースはルート
  • コード外へ出ても調からは外れない
  • パターンを毎小節引き直さない
  • breakを長く続けない
  • DJミックスでベースと和音を二重に重ねない
  • リフの応答を無限に連鎖させない

これらは「確率0.8」のような好みではなく、システムが音楽として自壊しないための境界である。

2.2 語彙 ― 選択できる音楽的な身振り

例:

  • フレーズ: plateau / build / break / drop / dub-out
  • リフのリズム: quarter / eighth / three / laid / push / syncope
  • 遷移: break / morph / DJ mix
  • ハーモニー: stab / sustain / jazz
  • ドラム変形: 抜き / 食い / double / ghost
  • リフ変奏: 移調反復 / 反転 / 追加 / 削除 / rhythm variation

elevator-three は無限の音楽を直接探索するのではなく、人間が音楽的だと認めた語彙の組み合わせを探索している。

2.3 文脈依存規則 ― 同じ行為でも場面によって意味が変わる

例:

  • buildではシーケンスのdelayを深くする
  • 明るいコードではベースをルート寄りにする
  • 音程が動かないベースではfilter variationを増やす
  • ベース音符が少ない小節ではphaserを足す
  • stab群ではリフを落ち着いた型へ寄せる
  • funk群ではpushやthreeを好む
  • break中にはspark riffを出さない
  • dubの1小節ではdryを消すが、delay/reverb returnは残す

この層があるため、パラメータ変更が単なる「値の変化」ではなく編曲上の意味を持つ。

2.4 確率的嗜好 ― 必須ではないが、その音楽らしさを作るもの

確率は「何でもあり」にするためではなく、複数の妥当な候補のどれを今回採るかに使われる。

例:

  • 次のシーンは別群へ80%で渡る
  • リフから35%で応答する
  • リフ全体を30%で1オクターブ下げる
  • フィルが35%で次小節へはみ出す
  • industrial noiseの左右を70%で独立周期にする

確率値は音楽的な癖として働く。

elevator-three では、この層の一部が Jev に置き換わった。次のシーン、渡し方、次のシーンの長さ、フレーズ型、4小節の節目の仕掛け、dub、キーと進行、転調、開いた和声、新しいリフの旋律。これらは Jev が返す確率に従って引く。jev スライダーの値 (既定 1) がその割合で、残りは elevator-two と同じ固定の確率で引く。固定の確率は、答えが間に合わないときの既定としても残る。

固定の癖が、流れを読んだうえでの判断に変わった、ということもできる。ただし、上の例のうちリフの応答、オクターブ下げ、フィルのはみ出し、ノイズの周期は、いまも固定の確率のままである。

2.5 記憶 ― 過去との関係を作る知識

elevator-threeには複数の時間幅の記憶がある。

  • 直近に使ったシーン
  • 現在のpattern seed
  • ベース旋律のseed
  • 偶数／奇数小節の2小節構造
  • 直前のspark motif
  • motifの寿命
  • 呼びかけに対する予定された応答
  • 現在の陰陽波の位置
  • Jev に渡す出来事の履歴 (シーン、フレーズ、仕掛け、dub、リフ、キーを、種類ごとに直近8件)

これによって現在の演奏が、過去から独立した乱数列ではなくなる。

最後の履歴は elevator-three で加えた記憶で、楽器自身は読まない。Jev に「ここ数分に何が起きてきたか」を伝えるためだけにある。

特にspark motifは、絶対音程ではなく和音内の相対的な動きを記憶する。これは「音そのもの」ではなく「音楽的関係」を記憶している例である。

2.6 忘却 ― 同じ知識を永久に使わないための知識

記憶と同じくらい重要なのが忘却である。

モチーフは2〜4回使えば引退する。シーンが変われば捨てる。直近のシーンは次の候補から避ける。

これは、生成システムにとって重要な原則を示している。

反復には記憶が必要だが、展開には忘却が必要である。

3. 状態モデル ― アプリは何を「現在」として認識しているか

elevator-three が判断に使う状態は、単一の変数ではない。

GLOBAL
 ├─ 陰陽波の位置
 ├─ BPM
 ├─ key
 └─ user controls

SCENE
 ├─ scene identity
 ├─ group / circuit
 ├─ kit
 ├─ density / glitch tendencies
 └─ scene age

PHRASE
 ├─ plateau / build / break / drop / dub-out
 ├─ phrase position
 └─ layer state

BAR
 ├─ bar number
 ├─ fill?
 ├─ dub?
 ├─ event?
 ├─ bass note count
 └─ transition proximity

MOTIF / PATTERN MEMORY
 ├─ rhythm seed
 ├─ bass seed
 ├─ spark motif
 ├─ motif life
 └─ pending response

したがって、同じ16分位置でも、その瞬間の意味は状態によって変わる。

「step 12だから音を鳴らす」のではなく、

「陽へ向かっている曙のbuild後半で、8小節の折り返しに近く、ベースは疎で、前の区間にsparkの呼びかけがあった」

という状態を背景に、実際の音が決まる。

elevator-three は、この状態の一部を文字にして Jev に渡す。シーンの名前と性格の説明、フレーズとその経過、陰陽の波の位置と向き、キーと和音、密度・glitch・evolution の値、そして上の履歴である。Jev は音を聴けないので、これが Jev にとっての「いま」のすべてになる。

4. 判断は時間階層ごとに分業される

音楽知識モデルとして見ると、elevator-threeは一つの巨大な判断器ではなく、異なる時間感覚を持つ複数のエージェントに近い。

4.1 Composer ― 長期構成

時間幅: 20〜40分〜数分

判断:

  • 陰から陽へどう移るか
  • 次にどのscene familyへ行くか
  • 同じ場所に留まりすぎていないか
  • BPMやkeyをどう乗り換えるか

目的:

長く聴いたときに「大きな呼吸」を作る。

elevator-three では、次のシーン、渡し方、長さ、行き先のキーと進行を Jev に相談する。問い合わせるのは、乗り換えの8〜16小節前である。

4.2 Arranger ― フレーズ構成

時間幅: 8〜16小節

判断:

  • plateauを続けるか
  • buildするか
  • dropするか
  • 一瞬breakするか
  • dub-outへ行くか
  • layerを何枚出すか

目的:

現在の素材を使って起伏を作る。

elevator-three では、フレーズ型を Jev に相談する。ただし候補は、そのシーンが出しうる型に限る。

4.3 Section editor ― 4〜8小節の句読点

判断:

  • fillを入れるか
  • filter sweepを入れるか
  • kick/hatを抜くか
  • glitchを入れるか
  • spark riffを呼ぶか
  • dubを起こすか

目的:

長い反復の中に節目を聞かせる。

elevator-three では、4小節の節目の仕掛け (「何もしない」を含む) と dub を Jev に相談する。フィルの置き場所と spark riff を呼ぶかどうかは、手元の規則のままである。

4.4 Players ― 各楽器の演奏判断

各楽器は同じ生成方式を共有しない。

  • drummerは拍の骨格を守る
  • bassistは和声と音色の両方を演奏する
  • harmony playersは回路ごとに異なる奏法を持つ
  • sequencerは少数音を反復しながら空間を開く
  • spark playerはモチーフを記憶し変奏する
  • industrial layerは小節線から意図的に外れる

目的:

楽器の役割に応じた自由を与える。

Players の判断は Jev に相談しない。例外は spark player で、新しい旋律を弾くときだけ、6通りの候補のどれを弾くかを Jev が選ぶ。

4.5 Mixer / dub engineer ― 音響も編曲として扱う

判断:

  • filterをどこまで開くか
  • delay feedbackをいつ上げるか
  • dryをいつ消すか
  • phaserをいつ使うか
  • resonanceを上げたとき量をどう補正するか

目的:

音響操作を「後処理」ではなく演奏行為にする。

Mixer の判断も Jev に相談しない。

5. 判断の基本形は「条件 → 候補 → 制約 → 重み → 行為」

多くの判断は、概念的には次の形に整理できる。

1. 現在の状態を読む
2. 今回選べる候補を作る
3. 音楽的に不適切な候補を除く
4. 残った候補に文脈依存の重みを付ける   ← elevator-three では Jev が付ける
5. 必要なら確率で一つ選ぶ               ← Jev の確率に従って引く (最大確率は取らない)
6. 演奏行為へ変換する
7. 必要な記憶を更新する

elevator-three が置き換えたのは 4 と 5 だけである。候補を作る 2 と、除く 3 は音楽知識の仕事のまま残る。Jev は流れを読む重み付けの係であって、何が音楽として許されるかは決めない。

たとえば次のシーン選択なら、

陰陽波の現在位置
      ↓
近いシーンを候補化
      ↓
直近のシーンを除外
      ↓
波に近い6つに絞る
      ↓
Jev に、候補の性格の説明とここ数分の履歴を見せる
      ↓
Jev の確率に従って scene決定   (elevator-two では「別群を80%で優先」)
      ↓
遷移可能性を確認 (morph は同じ群・同じキットだけ)
      ↓
break / morph / mix を Jev の確率に従って決定

spark riffなら、

4小節区間の開始
      ↓
break中ではない?
      ↓
出現間隔を満たす?
      ↓
呼びかけか応答か?
      ↓
scene groupからrhythm profile
      ↓
新規motif or remembered motif
      ↓
新規なら同じ音数で6通り作り、Jev に選ばせる (3小節先に置いて答えを待つ)
      ↓
variation
      ↓
register / timbre contour
      ↓
配置して演奏
      ↓
motif lifeを更新

この形は、将来新しい知識を追加するときの共通フレームとして使える。

6. 「音楽的制約」は生成能力を狭めるのではなく、意味を作る

elevator-threeでは制約が非常に多い。

一見すると、生成AI的な自由度を下げているように見える。しかし実際には逆である。

たとえば、

  • キックを普段は崩さないから、崩した瞬間が意味を持つ
  • breakを短くするから、休止が句読点になる
  • motifをそのまま永久反復しないから、再登場が記憶として働く
  • リフを常時鳴らさないから、登場が合図になる
  • ベースの音程を増やさないから、filter movementが演奏として聞こえる
  • DJ mixでdrumsだけを重ねるから、scene transitionが濁らない

つまり制約は「できないこと」ではない。

差異を知覚可能にするための背景である。

elevator-three では、制約にもう一つの役目が加わった。判断を外部に委ねても、骨格が壊れないようにすることである。Jev は候補の外を選べず、候補は制約を通ったものだけでできている。Jev の答えが的外れでも、答えが来なくても、鳴るのは音楽として許された範囲の中である。制約があるから、判断を安心して委ねられる。

7. 反復・変奏・対比・休止 ― 四つの基本操作

現在の実装を抽象化すると、elevator-threeの編曲は主に四つの操作からできている。

反復

pattern seed、bass seed、2小節単位の顔、持続するscene identity。

聴き手に「いま何が鳴っているか」を覚えさせる。

変奏

mutate、fill、spark motif variation、filter wobble、octave displacement、rhythmic type。

覚えたものを壊さず、新しさを与える。

対比

陰↔陽、stab↔sustain、暗いkit↔electro kit、plateau↔build/drop。

局所的変化では作れない大きな違いを作る。

休止

break、kick/hat抜き、dub dry cut。

音を追加せず、欠落によって構造を聞かせる。

この四つを時間階層ごとに組み合わせることが、elevator-threeの編曲の基本文法といえる。

Jev が主に関わるのは、このうち対比と休止の置き方である。いつ別の群へ渡るか、いつ break や dub で抜くか、いつ何も起こさずに反復を続けるか。

8. 音高・リズム・音色・空間を同格の演奏パラメータとして扱う

一般的な自動作曲では、音高とリズムを生成し、その後に音色を当てる構造になりやすい。

elevator-threeでは、これは当てはまらない。

ベースでは、音程が単純ならfilter movementが増える。spark riffでは、旋律と同時にcutoff、Q、decayのフレーズ内輪郭が決まる。dubでは、dryとdelay returnの関係そのものが1小節の演奏になる。buildでは、シーケンスのping-pong delayが深くなり、音像が広がる。

したがって、elevator-threeの「ノート」は概念的には、

note =
  pitch
+ onset
+ duration
+ velocity
+ timbre trajectory
+ spatial behavior
+ structural role

として扱ったほうが実態に近い。

9. 知識には「由来」と「確信度」がある

elevator-two の設計の記録 (two-DESIGN.md) を見ると、多くの規則は最初から理論的に決められたものではない。

「聴いた結果の指摘から」という記録が何度も現れる。

たとえば、

  • breakは16小節では長すぎた → 1小節へ
  • ベース旋律が毎小節変わると落ち着かない → seedを保持
  • デチューンだけではベースが薄い → PWMを導入
  • 持続和音が前に出すぎる → bus levelを下げる
  • リフのミクロな揺らぎは耳に届かない → フレーズ単位の音色輪郭へ
  • 乱数を増やしても変奏にはならない → motif memoryを導入

つまり、この知識ベースは「音楽理論集」ではなく、仮説 → 実装 → 試聴 → 修正で育った経験知である。

将来このモデルを明示化するなら、各知識に次のメタデータを持たせる価値がある。

Knowledge Rule
 ├─ statement      何を知っているか
 ├─ scope          どの時間階層／楽器に効くか
 ├─ condition      いつ適用するか
 ├─ action         何をするか
 ├─ invariant      絶対条件か
 ├─ weight         嗜好ならどの程度か
 ├─ memory         何を参照・更新するか
 ├─ rationale      なぜそうするか
 └─ evidence       試聴・実測・設計判断

これは、今後Claude Codeや別のAIと開発を続ける際にも有効である。

elevator-three では、Jev の答えそのものが確信度を持つ。Jev は選択肢ごとの確率に加えて confidence を返す。これを、ある判断をどこまで Jev に委ねるかの手がかりにできる。

由来についても、試聴から学ぶ流れは変わらない。本物の Jev で鳴らしてみると、4小節の節目の仕掛けについて Jev は「何もしない」を5〜7割選び、手元の規則より仕掛けが控えめになった。これも、次に質問文を詰めるための経験知である。

10. 現在の知識モデルの強み

局所ランダムに陥らない

長期波、scene、phrase、bar、stepが分離されているため、16分音符の変化がそのまま曲全体の迷走にならない。

楽器の役割が保たれる

全トラックに同じ生成器を使わず、kick、hat、bass、harmony、riffがそれぞれ別の「常識」を持つ。

記憶がある

patternとmotifが過去を参照するため、「前に出たものが戻る」が成立する。

音響が作曲から分離していない

filter、delay、resonance、stereo imageまで構成要素になっている。

人間が介入できる

完全自律ではなく、陰陽、密度、evolution、mutate、scene selection、nextなどで、人間が高位の意図を与えられる。jev スライダーで、判断をどこまで外部に委ねるかも決められる。

判断を外部に委ねられ、委ねても骨格が壊れない

重み付けの段だけを Jev に開いたので、流れを読んだ判断を外から借りられる。一方で、候補と制約は手元に残るので、答えが外れても、来なくても、音楽は成立し続ける。

11. 現在のモデルにまだ明示されていないもの

ここからは「現状に存在しない機能」の提案ではなく、現在の資料からは明示的なモデルとして確認できない領域を区別しておく。

聴覚的な自己評価

現在は「自分が今どのくらい混雑して聞こえているか」「直前の結果が良かったか」を音声解析して判断する仕組みは、資料上の中心モデルにはない。

判断は主として内部状態とルールから行われる。Jev も音を聴かず、言葉と記号にした状態から判断している。

長期的な学習

試聴結果は人間との開発対話を通してDESIGN.mdとコードへ反映されてきたが、実行中のアプリ自身が「この演奏は良かった」と学習してルールを書き換えるわけではない。Jev も、送られた入力をもとに学習することはない。

意味的な曲想

陰陽やscene personalityはあるが、「悲しみ」「緊張から解放」「夜明け」といった物語意味を理解して作曲しているわけではない。名前は人間が与えた音楽的メタファーである。

elevator-three では、この領域に少しだけ手が入った。Jev はシーンの性格を言葉で書いた説明と、ここ数分の流れを読んで判断する。ただし、それが「意味を理解した」判断かどうかは、まだ確かめられていない。確かめられるのは、答えの確率と、それを使って鳴らした結果だけである。

この境界を明確にしておくと、現在のシステムの強さを過大評価せずに済む。

12. 将来の開発で、このモデルをどう使えるか

新機能を「音を増やすIssue」として考える代わりに、次の問いを使える。

  1. これはどの時間階層の知識か？
  2. どの状態を観察して判断するのか？
  3. 守るべき不変条件は何か？
  4. 候補となる音楽語彙は何か？
  5. 確率に任せる部分と、規則で決める部分はどこか？ 流れを読む必要があるなら、Jev に相談する判断か？ そのとき候補は誰が作り、答えが来ないときはどう決めるか？
  6. 過去の何を記憶する必要があるか？
  7. いつ忘れるべきか？
  8. 結果は音高・リズム・音色・空間・休止のどこへ作用するか？
  9. 人間の操作はこの判断へどう介入するか？
  10. 試聴して何をもって成功と判断するか？

この10問に答えられれば、新しい仕掛けも既存の音楽システムへ自然に接続しやすい。

13. elevator-three の知識モデルを一文で表す

elevator-threeは、

複数の時間階層にわたる音楽状態を保持し、楽器ごとの役割、不変条件、文脈依存規則、短期記憶と忘却を使って候補を作り、その重み付けの一部を流れを読む外部のモデルに相談しながら、反復・変奏・対比・休止をリアルタイムに編成する知識駆動型の自動演奏システム

と捉えることができる。

ここで最も重要なのは「自動」であることより、何を知っているから、その判断をしたのかを説明できることだ。

elevator-two の面白さは、ニューラルネットワークの内部に暗黙知を閉じ込めるのではなく、人間とAIの対話で得た音楽的判断を、かなりの部分まで明示的な規則としてコードに残している点にあった。elevator-three はその規則を残したまま、モデルに任せる範囲を「候補の重み付け」だけに限った。何を相談し、何を返され、何を使ったかは、monitor にそのまま出る。判断の説明可能性は保たれている。

それは同時に、次にどんな音楽知識を教えるべきかを、人間が考え続けられる構造でもある。
